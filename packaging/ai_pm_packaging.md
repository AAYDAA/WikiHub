> 面向 AI 产品经理岗。核心叙事：**亲手搭了一条完整 RAG 链路，用一套可量化的评测体系完成两轮"数据/策略驱动"迭代——发现问题（人物问答 0% 命中）→ 修复 → 再优化，全程用指标把关，还拦下过一版会导致效果崩盘的坏改动**。证明的不是"会写代码"，而是"能定义场景、用数据做决策、理解 AI 产品边界与成本"。

## ① 一页纸项目介绍（作品集 / 自我介绍口播稿）

**WikiHub — 游戏 Wiki 智能问答（RAG 应用）**

**一句话**：面向《以撒的结合》新手玩家的 AI 问答助手，用自然语言提问（"硫磺火有什么效果？"），系统从 893 个 Wiki 页面中检索证据并生成带原文链接的答案。

**为什么做**：游戏 Wiki 信息密度高、新玩家检索成本大；通用 AI 助手不接实时知识库、会编造。做一个"答得准、给得出处、可验证"的垂域问答。

**我做了什么（产品视角）**：
- **定义用户与场景**：锁定新手玩家 4 类高频问题——道具效果 / 解锁获取 / 人物角色 / 机制攻略，据此设计评测题集
- **搭完整链路**：Wiki 数据抓取 → 清洗切分 → 向量化建库（本地 BGE 中文模型，离线可跑）→ 检索增强生成（DeepSeek），答案附原文来源链接
- **第一轮迭代（数据驱动）**：自建 20 题评测发现"人物角色"类 **5/5 题检索失败（0% 命中）**，定位到数据采集的分类名错误导致人物内容整体缺失（MediaWiki 对不存在的分类返回空列表而非报错，属"静默故障"）→ 补抓 34 个人物页重建索引 → 人物类 **0% → 100%**
- **第二轮迭代（策略驱动，评测把关）**：针对"标题混淆/小节排位"设计轻量混合重排（向量为主 + 标题命中加权）→ 首版排序方向写反导致 Top1 从 90% 崩到 45%，**被评测当场拦下**；修复后 Top1 达到 **100%**、小节精确率 57.1% → **71.4%**
- **整体量化**：20 题评测上 Top1 命中率 70% → **100%**，MRR 0.725 → **1.000**，小节精确率 57.1% → **71.4%**

**成本与工程意识**：Embedding 模型本地化（省 API 成本、离线可用）；评测刻意只测检索不测生成（生成依赖付费 LLM key，控制验证成本）；重排权重参数化、可 A/B 开关。

**局限与规划**（诚实 + 有 roadmap）：评测题集仅 20 题，重排参数存在"在题集上过拟合"的风险，下一步需扩充题集/预留验证集；小节级仍有 2 题 miss（页面本身缺「解锁」小节，属数据缺口）；生成质量尚未系统评测。后续规划：多轮追问、坏例反馈闭环、生成抽评、多游戏接入与问题路由。

**数据合规**：内容来自灰机 Wiki（开放授权），仅学习用途。

## ② 简历项目条目（AI 产品方向 · STAR 结构）

> 放在"项目经历"，标题可写 **WikiHub · 游戏 Wiki 智能问答产品（个人项目）**，角色可写 **产品与全链路实现（1 人）**。

**版本 A：要点式（投简历用）**

- 面向《以撒的结合》新手玩家定义 4 类核心问答场景（道具效果/解锁获取/人物角色/机制攻略），独立完成 Wiki 数据采集、清洗切分、向量检索到 LLM 生成的 RAG 全链路
- 搭建 20 题场景化评测体系（Top1/Top3 命中率、MRR），数据定位"人物问答 0% 命中"根因（分类名错误致内容静默缺失）→ 补数据后 **0% → 100%**；第二轮混合重排优化经评测把关，修复首版回归后将 Top1 提升至 **100%**、MRR 0.725 → 1.000
- 成本敏感设计：Embedding 本地化省 API 费用；评测仅覆盖检索、生成按需抽验；优化参数可 A/B 开关，坏改动在上线前被评测拦截

**版本 B：一段式（求职信/作品集描述）**

> 为验证"AI 能否可靠回答垂域问题"，我独立设计并实现了一款基于 RAG 的游戏 Wiki 问答产品。先定义新手玩家 4 类高频场景并建立 20 题量化评测集，随即发现人物类问答 0% 命中——定位为采集环节分类名错误导致的"静默数据缺失"（系统不报错、数据为空），补数据重建后该类命中率升至 100%。第二轮针对标题混淆设计混合重排，首版因排序方向错误被评测发现效果崩盘（Top1 90%→45%），修复后整体 Top1 命中率 70%→100%、MRR 0.725→1.000、小节精确率 57.1%→71.4%。全程坚持成本意识（本地化 Embedding、评测仅在必要时调用付费模型），并用"每次改动跑回归"保证指标只升不降。

## ③ 面试故事线（讲的时候按这个顺序，别讲技术实现细节）

1. **先给场景**："以撒新手查 Wiki 很累，我观察 4 类最高频问题…" → 证明你会定义用户需求
2. **再给方案**："RAG = 先检索证据、再让模型基于证据回答、并给出处" → 一句话讲清原理
3. **第一轮迭代（重点）**："上线后我用自建评测跑 20 道题，发现人物类全挂——**0/5**。这不是模型问题，是**数据问题**：我采集时把分类名写错了（Wiki 上叫「人物」，我写的「角色」），MediaWiki 查不到就返回空列表，**系统一声不吭**——数据悄悄丢光了你都不知道。我补了数据，再加了一道**覆盖率校验**：以后任何分类抓到 0 页当场报警，这类故障不可能再静默发生。"
4. **第二轮迭代（展示"评测驱动"的方法论）**："数据补齐后我继续抠指标，发现还有两类检索短板：易混标题（'圣心'和'圣饼'）和答案小节排位。我设计了一版轻量重排，结果第一版上线前跑评测——**Top1 从 90% 崩到 45%**，直接被拦下。查下来是排序方向写反了，修复后再跑：Top1 100%、MRR 满分。**如果没有这套评测，这版坏改动会静默上线伤害所有用户。**"
5. **量化收尾**："三轮数字：人物类 0%→100%；整体 Top1 70%→100%；MRR 0.725→1.000；小节精确率 57.1%→71.4%。"
6. **留有余地（展示产品嗅觉与诚实）**："我知道边界在哪：题集只有 20 题，重排参数是在这套题上调出来的，**有过拟合风险**，下一步要扩题集、留验证集；剩余 2 题小节 miss 查下来是页面本身缺'解锁'小节，属于数据缺口不是排序问题；生成质量也还没系统评。**知道自己不知道什么，也是产品能力。**"

**口播时间**：约 2.5 分钟。记住数字：893 页 / 8465 块 / 20 题 4 类 / 0%→100% / 70%→100% / MRR 1.000 / 45% 崩盘事件。

## ④ 高频追问与答法（提前准备）

| 可能被问 | 参考答法 |
|---|---|
| 为什么自己搭，不用现成 ChatGPT？ | 通用模型不接实时知识库、易编造；垂域问答要"有出处可验证"，这正是 RAG 的价值场景 |
| 怎么衡量"答得好不好"？ | 分两层：检索层可自动化量化（命中率/MRR，我做了且全流程用它把关）；生成层依赖人工与 LLM-as-judge，成本高，按需小样本抽验 |
| 检索 100% 了，答案就一定对吗？ | 不一定——生成层仍有幻觉风险；另外 100% 是 20 题集上的结果，样本小、有调参过拟合风险，需要扩题集验证。产品上用"附原文链接"兜底，真正的解法是用户反馈闭环 |
| 数据版权问题？ | 灰机 Wiki 基于开放授权（CC BY-SA 类），个人学习用途；商业化前需确认授权范围与爬取策略 |
| 只接了 1 个游戏，怎么体现"产品"？ | 架构按"配置一个 Wiki 即可接入"设计；规划是问题自动路由、跨游戏对比问答、增量更新 |
| 如果继续做，优先级怎么排？ | ① 扩充评测题集 + 留验证集（治过拟合）② 坏例反馈闭环（答案质量发动机）③ 多轮追问 ④ 游戏路由（从 1 到 N 的前提）⑤ 增量更新与数据质量监控 |
| 一个人又做产品又做实现，时间怎么分？ | 先用最小场景跑通验证价值，再集中资源在"数据质量"与"评测"上——因为检索效果 = 数据质量 + 检索策略，前者是根因（0%→100% 案例），后者靠评测把关（45% 崩盘案例） |
| 有没有"发现了一个别人发现不了的问题"的例子？ | 有两个：一是静默数据缺失（MediaWiki 分类名写错不报错只返回空，没有覆盖率校验就永远发现不了）；二是自己的坏改动被评测拦下（排序方向写反，Top1 90%→45%）——后者恰好证明了评测体系值得投入 |
| 指标全绿就代表产品成功吗？ | 不是——命中率衡量"找到没找到"，不衡量"答案好不好用"。真正的北极星应是用户能否一次问对、信任答案；所以我下一步优先做反馈闭环而不是继续刷检索指标 |

## 附：真实数据速查（面试别记错）

- 数据：6 分类（道具 500 / 饰品 188 / 卡牌 97 / 胶囊 50 / 人物 34 / 房间 24）共 893 页，切分为 8465 块

- 数字：人物类 0→100% · Top1 70%→100% · Top3 75%→100% · MRR 0.725→1.000 · 小节精确率 57.1%→71.4%
- 方法论事件：重排 v1 致 Top1 90%→45%（评测拦截）→ 修复后 100%
